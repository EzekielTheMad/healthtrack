## Safe document imports

Lab PDFs and complete medical histories use one durable review ledger.
Extraction stages claims separately from accepted clinical records. Check the
patient and original document before applying decisions. Complete-history
originals remain owner-only even when extracted labs are shared. Ordinary lab
files retain their existing exact patient/section sharing checks.

The SHA-256 file hash is scoped to account, selected patient and importer kind.
Uploading the same bytes through the same importer resumes its saved batch; it
does not replay completed decisions. Settings → Data & reports → Import Medical
History lists saved document reviews, including lab reviews. Another patient
has a separate batch.

| Classification     | Meaning                                                                     |
| ------------------ | --------------------------------------------------------------------------- |
| New entry          | No candidate with that name was found.                                      |
| Possible match     | Similar record or ambiguous event identity; review is required.             |
| Conflicting values | A dated candidate has incompatible known values.                            |
| Exact match        | Complete compared content and sufficient identity agree with one candidate. |

A name match does not prove duplication. The same lab name, date and value can
represent multiple draws. Exact lab matching requires positive
specimen/accession/collection-time evidence without contradictory known
identity fields; units remain case-sensitive. Cross-page extraction retains
different or richer claims instead of silently choosing one.
Printed LOINC codes are preserved through extraction, review, saving and
corrections. Matching nonempty codes can identify candidates with different
printed names; conflicting codes prevent an exact match. A shared code alone
still does not prove the same draw. Without a name/code candidate, an exact
date/value/unit match with compatible specimen evidence can surface a possible
alternative for human review. It never confirms a duplicate across different
names without the same printed code. No code is inferred from a name, and no
terminology lookup or guessed synonym is used.

| Decision       | Effect                                                                                                                                |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| Keep in review | Leave the item pending.                                                                                                               |
| Skip           | Record the decision without changing clinical data.                                                                                   |
| Add separately | Create a distinct record; if the server proves an exact duplicate during commit, associate the source with that existing record.      |
| Link           | Associate the source claim with the selected record without changing clinical values.                                                 |
| Correct        | Update reviewed fields while retaining previous values and the reason. A stale review cannot overwrite a subsequently changed record. |

Commit uses a SQLite immediate transaction and a savepoint per item. A failed
item rolls back its own clinical writes and remains retryable; successful
items stay durable. Counts distinguish `applied`, `linked`, `corrected`,
`skipped`, `pending` and `error`. Retries do not create another record for a
previously applied item. The ledger retains extracted and accepted payloads,
plus source/page evidence when available. Saved lab editing uses stable result
IDs and cannot replace the original file or delete sibling tests.

| Method     | Session-authenticated route            | Purpose                                                           |
| ---------- | -------------------------------------- | ----------------------------------------------------------------- |
| POST       | `/api/parse-lab-pdf`                   | Validate bytes, extract and stage a lab batch.                    |
| POST       | `/api/parse-medical-history`           | Extract and stage supported clinical domains.                     |
| GET        | `/api/import-batches?dependent_id=...` | List the owner's reviews for exactly one patient.                 |
| GET / POST | `/api/import-batches/{id}`             | Read review state / apply explicit decisions.                     |
| POST       | `/api/import-medical-history`          | Compatibility entry point through the same ledger/commit service. |
| PATCH      | `/api/labs/{id}`                       | Correct a visit and supplied stable-ID results with an audit.     |

Import mutations are owner-only, including the owner's dependents; they do not
grant delegate/PAT write access. The old standalone lab-save route returns
`409 review_required` for a staged source so it cannot bypass the review.

### Limits, uncertainty and retries

- Standalone labs: 10 MB. Complete histories: PDF up to 50 MB and 200 pages;
  images up to 10 MB. History PDFs over 30 pages use sequential 25-page chunks.
  A document is limited to 2,000 staged claims.
- PDF, PNG and JPEG are detected from signatures. Empty/wrong browser MIME
  does not turn an image into a PDF. Recognizable file contents are required.
  Provider limits and proxy timeouts can still reject a request.
- Partial dates remain `YYYY` or `YYYY-MM`; unknown dates remain unknown.
  Required clinical dates need an exact reviewed date. Nothing defaults an
  absent collection date to today or invents January 1.
- Multi-draw lab reports retain per-result collection dates and specimen
  context. Ambiguous dates stay staged. Check historical comparison columns
  against the original; AI extraction is not verification.
- Qualitative-only results such as “Negative” or “Reactive” are not represented
  by the numeric lab schema and are currently skipped during extraction.
  Preserve the original and use a clinical note where appropriate. Numeric
  thresholds such as `<5` retain printed text in staging and cannot be saved as
  an exact number; keep them in review or skip them.
- Failed history chunks produce page-range warnings. Even when all extracted
  items are resolved, failed sections keep a batch `incomplete`. Reupload the
  same file for the same patient with **Retry an incomplete extraction**
  selected. This uses AI again and may process the whole document. Recovered
  or changed claims are appended to the existing ledger; applied records are
  not replayed. New matches still require review. If every chunk fails, no
  successful extraction is reported.
- `complete` means staged supported claims were resolved without an outstanding
  extraction failure. It does not prove that every printed source row was
  represented or that the clinical content is correct.

## Operator upgrade and restore

Follow [release verification](RELEASE.md). Preserve effective operator values;
do not replace an applied Unraid template with repository defaults or put
credentials in commands, logs, examples or release evidence.

1. Record the current immutable image identity, intended access URL, data
   mount and configuration. Keep the current install working while checking
   the candidate in isolation.
2. **Confirm the calendar timezone before ingestion or nutrition
   reprocessing.** Older Health Connect normalization used
   `America/Phoenix`; this candidate uses configured `TZ`, falling back to
   `Etc/UTC`. Verify the intended timezone against historical day assignments,
   including readings near midnight. An existing Phoenix-based installation
   should explicitly retain `America/Phoenix` unless a separate date-conversion
   plan is approved. There is no automatic stored-date migration. A timezone
   change followed by reprocessing can assign different canonical days.
   The live Unraid timezone has not been verified by these local changes.
3. Before an authorized upgrade, stop writes and consistently back up the
   whole `/data` tree: database, uploads and generated keys. Preserve externally
   supplied secrets in protected configuration backups. Retain the prior
   immutable image and its configuration with the snapshot.
4. Test migrations and restore in isolation. Routine regressions use synthetic
   records. An operator-authorized drill with an actual backup must remain
   private and isolated. Disable native scheduling in the test copy
   (`OURA_SYNC_ENABLED=false`), avoid real provider calls and do not direct
   bridges at it. Do not reprocess production data as a test.
5. Startup applies migrations automatically. This candidate adds import/audit,
   integration freshness and context-evidence storage. Verify sign-in, exact
   patient isolation, medication dates, import/resume/correction, original-file
   access, source selection and the downloaded PDF. Health alone proves none
   of these workflows.
6. Use the intended `APP_URL`. LAN HTTP uses an exact `http://host:port` origin
   and functional non-Secure session cookies. HTTPS origins need Secure
   cookies even behind a proxy forwarding HTTP internally. See [cookie
   verification](RELEASE.md#release-evidence-requirements).
7. For an authorized rollback, stop the candidate, retain its data separately,
   and restore the complete pre-upgrade snapshot with its compatible prior
   image/configuration. An image rollback alone does not undo migrations.
   Verify sign-in, records, originals and integration state before resuming
   writes or ingestion. Having a backup is not a successful restore drill.
